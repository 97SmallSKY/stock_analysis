## 根因

**开发假定错配 API 字段 = DB 列**。

具体链路:
1. 体检发现 `/api/dashboard` 返回 `sentiment.total_stocks = null` 等 3 字段空白
2. 以为是后端写入缺列,于是在 `writer.upsert_market_sentiment.cols` 加上 3 个字段
3. **没有验证表结构**,直接假定表里有这 3 列
4. 实际上查 `information_schema.columns` 会发现**这 3 列从未被建**
5. `api/dashboard.py` 旧代码通过 `out.setdefault("total_stocks", None)` 在 JSON 响应层「硬塞」占位,视觉上像是字段存在
6. 回填时 `INSERT INTO market_sentiment (... total_stocks ...)` 直接抛 `UndefinedColumn`

### 代码对照

**误以为的表**(实际根本没加这些列):
```python
# backend/db/writer.py(P18.13 错误版本)

        "strong_stock_count", "weak_stock_count",
```

## 教训

### 🔴 核心教训(已写入 Agent 手册 3.2 节)

**改 writer + schema 的改动**,必须先用 `information_schema.columns` 验证真实 DB schema,**不能假定 API 字段 = DB 列**。

### 流程层面

1. **写代码前 read schema**:改动涉及任何数据库表写入前,先用 `psql \d table_name` 或 `information_schema.columns` 查清楚现有列
2. **看 API 代码全貌**:API 层可能对响应做字段补齐/转换,不能仅凭 JSON 响应反推 DB
3. **回填前试点**:大批量回填前先跑单日验证,比如 `run("20240229", "20240229")` 看是否能入库

### 技术层面

1. **早期发现**:事故爆发 <1 分钟就被发现(pkill 第二条 log 就停了),得益于自动化回填日志的即时观察
2. **快速回滚能力**:从发现 → 提交 P18.13b → 部署完成 **仅用 9 分钟**,证明 git 闭环流程有效
3. **API 层弹性**:API 里的 `setdefault` 容错反而掩盖了 schema 缺失,应当考虑用**更严格的 Pydantic 响应 schema** 在测试期间就暴露这种不一致

### 监控层面

4. 当前**没有对 sentiment 表的关键字段做告警**。未来可加:
   - DB 行数上涨但 `up_down_ratio` 仍为 NULL 的日数达阈值时告警
