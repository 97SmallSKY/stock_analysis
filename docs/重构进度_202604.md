## 二、已完成工作详情

### Phase 1：新建 `modules/scorer.py`（统一评分引擎）

**完成时间：** 2026-04-01

**背景：**
在审查中发现技术面/资金面评分逻辑在以下 3 处独立实现（逻辑高度相似但参数签名不同）：
- `pages/lhb_signal.py` 的 `_score_tech()` / `_score_fund()`（含 `seat_df` + `fund_flow` 参数）
- `skills/stock_sim_robot/fetch_signal.py` 的 `_score_tech()` / `_score_fund()`（轻量版，无 Streamlit）
- `modules/analyzer.py` 的 `calculate_technical_score()`（回测用）

**改动内容：**
1. 新建 `modules/scorer.py`，提供三个统一出口函数：
   - `score_tech(kline, trade_date, lianban_count=0)` — 技术面评分（最高40分，含连板因子）
   - `score_fund(lhb_row, seat_df=None, fund_flow=None)` — 资金面评分（最高35分）
   - `score_history(hist_dict)` — 历史胜率评分（最高25分）
2. `pages/lhb_signal.py`：删除内置 `_sma/_ema/_score_tech/_score_fund/_score_history`，改为薄包装调用 `scorer`
3. `skills/stock_sim_robot/fetch_signal.py`：同上，删除约 280 行重复代码

**代码缩减：** 删除约 280 行重复评分代码（两处各 ~140 行），保留单一权威实现

**向后兼容性：**
- 两处调用点保留同名包装函数 `_score_tech/_score_fund/_score_history`，函数签名不变
- `fetch_signal._score_fund()` 额外保留旧返回字段 `net_buy` / `duodao_reason`（部分调用方依赖）

### Phase 2：连板高度短线因子接入

**完成时间：** 2026-04-01

**背景：**
`modules/data_fetcher.py` 中的 `fetch_market_sentiment()` 已调用 `ak.stock_zt_pool_strong_em` 获取连板强势股池（含「连板数」字段），但该数据未注入评分引擎，导致龙虎榜打板机会被低估。

**改动内容：**
1. `modules/scorer.py` 的 `score_tech()` 新增 `lianban_count` 参数（默认0）：

   | 连板数 | 加分 | 说明 |
   |--------|------|------|
   | 0 | +0 | 普通龙虎榜标的 |
   | 1 | +4 | 首板，短线信号 |
   | 2 | +7 | 双连板，持续强势 |
   | ≥3 | +10 | 高位连板，强势共振 |

   加分叠加在技术面归一化分后，最终仍截断到40分上限。

2. `skills/stock_sim_robot/fetch_signal.py` 的 `get_mainboard_signals()` 在 Step 2 后新增 Step 2b：
   - 调用 `ak.stock_zt_pool_strong_em(date=trade_date)` 获取当日连板池
   - 构建 `{code: lianban_count}` 映射
   - 在 `_score_tech()` 调用时传入 `lianban_count=lianban_map.get(code, 0)`
   - 在返回信号字典中新增 `lianban_count`、`lianban_score` 字段

**数据获取策略：** 连板池数据获取失败时不影响其他评分（catch Exception，降级为0分）

### Phase 3：新建 `modules/market_data.py`（统一行情层）

**完成时间：** 2026-04-01

**背景：**
行情获取逻辑在以下 2 处独立实现：
- `modules/analyzer.py` 的 `_kline_get()`（带进程缓存，回测用）
- `skills/stock_sim_robot/trade_runner.py` 的 `_fetch_kline()` + `_get_t2_prices()` + `_get_nth_trading_day()`（无缓存，实时用）

主要风险点：两套交易日历实现和 T+N 日期计算逻辑不一致。

**改动内容：**
1. 新建 `modules/market_data.py`，提供：
   - `get_kline(code, trade_date, lookback, adjust)` — 带缓存，严格截断未来数据
   - `get_kline_raw(code, start_date, days, adjust)` — 无缓存，用于交易/实时场景
   - `get_t2_prices(code, trade_date, max_retries)` — T+2 价格（带重试）
   - `_get_nth_trading_day(base_date, n)` — 唯一的交易日历实现
   - `kline_cache_clear()` — 缓存清理（等效旧 `_kline_cache_clear`）

2. `modules/analyzer.py`：
   - `_kline_get()` 改为优先调用 `market_data.get_kline()`，失败时降级旧路径
   - `_kline_cache_clear()` 同步调用 `market_data.kline_cache_clear()`

3. `skills/stock_sim_robot/trade_runner.py`：
   - 在 `_fetch_kline()` 处添加注释，标注与 `market_data.get_kline_raw` 等效
   - 保留函数体不变（风险控制：trade_runner 是核心交易路径，不轻易改动）

**后续计划（下一 Phase）：**
待充分验证后，将 `trade_runner._fetch_kline/_get_t2_prices` 完全替换为 `from modules.market_data import get_kline_raw, get_t2_prices`，彻底消除重复。
