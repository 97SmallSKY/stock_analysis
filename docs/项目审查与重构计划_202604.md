# 龙虎榜量化策略系统审查与重构计划

## 1. 总体评价
当前项目已经初步跑通了从数据获取、策略评分、历史回测到模拟交易的完整端到端闭环，具备了一定的量化实战雏形。然而，作为一个面向量化实战的系统，当前架构在**逻辑高内聚**与**数据一致性**上存在严重缺陷。策略逻辑散落各处、UI与核心算法重度耦合，且表结构设计过于固化，不利于后续策略的快速迭代与多维度的回测对比。

---

## 2. 当前最大的核心问题 (Top 4 Issues)

### 2.1 核心策略逻辑严重散落耦合 (重度)
技术面、资金面的打分逻辑同时存在于以下四个不同的地方：
- `modules/analyzer.py` (内置 `calculate_technical_score`)
- `pages/mainboard_strategy.py` (内部硬编码 `_calc_composite_score`)
- `pages/lhb_signal.py` (页面内打分)
- `skills/stock_sim_robot/fetch_signal.py` (机器人的 `_score_tech`, `_score_fund`)

**痛点**：改动一处参数，其他地方不会同步，导致严重的逻辑割裂，页面选股与机器人选股标准不一致。

### 2.2 回测与模拟交易口径不一致 (中度)
回测引擎（`analyzer.py` 的 `simulate_with_stoploss`）的取价逻辑，与每日定时运行的模拟炒股机器人（`trade_runner.py`）使用了不同的获取路径。
**痛点**：回测表现极好，但模拟盘因为取价滑点、缺数据降级策略不同，产生“卖家秀与买家秀”的差异。

### 2.3 数据表设计固化限制扩展 (重度)
`sim_trades` 表结构将分批卖出策略（`sell1_pct`、`sell2_pct`）和具体维度的分析理由（`reason_tech`, `reason_fund`）硬编码成了表列（Columns）。
**痛点**：一旦策略改为“动态追踪止损”或“5档卖出”，就需要做数据库 DDL 变更，缺乏灵活性。

### 2.4 缺少短线/龙虎榜核心量化因子 (中度)
当前系统过度依赖传统中长线技术指标（MACD, RSI, MA），而对于短线龙虎榜打板策略而言，最核心的因子是缺失的。
**痛点**：容易买到跟风杂毛而非龙头。缺失的关键因子包括：**连板高度**、**首次封板时间**、**封单金额/流通市值比**、**所属热门概念**。

## 3. 最值得优先做的改造项（按优先级排序）

### P0: 抽离并统一全局「策略评分与选股引擎」 (高收益低风险)
- **动作**：新建一个独立的 `modules/strategy_engine.py`，将散落在各页面和脚本中的评分逻辑抽象为单例模块。回测模块、模拟机器人、前端页面全部调用该统一接口。
- **影响文件**：`analyzer.py`, `mainboard_strategy.py`, `lhb_signal.py`, `fetch_signal.py`

### P1: 重构 `sim_trades` 数据库表结构
- **动作**：将硬编码的离场规则打包移入 `exit_rules` (JSONB) 字段；将各项分析理由移入 `signal_metadata` (JSONB) 字段。提升扩展性。
- **影响文件**：`sim_trade_db.py`, `trade_runner.py`

### P2: 统一「行情获取与时间线」数据抽象层
- **动作**：将零散的 `_get_t2_prices`、`_fetch_kline` 统一到 `modules/market_data.py`。严格区分 `T日` 和 `当前机器时间`，确保回测不能取到未来函数数据。
- **影响文件**：`analyzer.py`, `utils/storage.py`, `trade_runner.py`

### P3: 引入打板与连板短线因子
- **动作**：在 `data_fetcher.py` 引入 AKShare 的每日涨停股池数据 (`stock_zt_pool_em`)，解析连板高度与核心题材，融合进评分引擎中。
- **影响文件**：`data_fetcher.py`, `scripts/daily_update.py`, `strategy_engine.py`

## 5. 页面与前端交互体验优化建议 (UI/UX Optimizations)

除了底层架构与算法的重构，针对当前 Streamlit 编写的 UI 页面，存在模块割裂、重算卡顿等痛点，提出以下 5 点深度改造建议：

### 5.1 操盘工作台化 (Command Center UX)
- **痛点**：目前模块割裂（实时大盘在 `realtime_monitor`，信号在 `lhb_signal`，交易在 `sim_trading`），用户体验像是“翻阅分散的报表”，而不是“盯盘交易终端”。
- **建议**：打造一个全局的“综合操盘工作台”。上半部分展示大盘动能与情绪指标，下半部分左侧滚动异动信号，右侧紧盯当前持仓盈亏。让开盘期间的核心决策能在一个页面内闭环。

### 5.2 交互式 K 线图与买卖点标记复盘
- **痛点**：在查看交易记录或选股信号时，只有干巴巴的表格数据，无法直观感受当时的技术形态，复盘极其不便。
- **建议**：集成专业金融图表（如 `pyecharts` 或基于 TV 的 `lightweight-charts-python`）。点击单笔交易即可展开 K 线，直接在图表上标注 `B(买入)`、`S(卖出)` 的确切位置，并叠加策略触发时的 MA/MACD/量比等副图指标。

### 5.3 全面升级高级表格组件 (Ag-Grid)
- **痛点**：当前大量使用的 `st.dataframe` 仅支持基础排序，无法对几百条龙虎榜数据进行组合条件过滤和直观的高亮预警。
- **建议**：全面启用并深度定制 `streamlit-aggrid`。实现前端的多列组合筛选（如：净买>3000万 且 换手率>5%）、列宽持久化、一键导出 Excel；并对“涨停/连板/高危”记录加入强烈的 Heatmap 颜色高亮。

### 5.4 局部刷新与防“闪烁”重绘 (Partial Rerun)
- **痛点**：Streamlit 的全量重绘机制导致用户在调整一个很小的下拉筛选条件时，整个页面（包括耗时的计算和图表渲染）都会重新加载，出现白屏闪烁和卡顿。
- **建议**：使用 Streamlit 较新的 `@st.fragment` 机制，将行情刷新区、图表展示区和表单控制区隔离开来。使得诸如“每 10 秒刷新大盘指数”的动作，不影响下方长耗时回测图表的渲染。

### 5.5 归因分析雷达图可视化
- **痛点**：当前在 `sim_trading.py` 里的选股理由是长串纯文本（`reason_tech` 等），不够直观。
- **建议**：为每只买入的股票生成一个“选股归因雷达图”（维度：资金强度、技术形态、历史胜率、席位质量、题材热度）。一秒钟看懂机器人为什么买它，并在平仓后做对比归因。

## 6. 建议的实施顺序

1. **统一引擎 (Phase 1)**：创建 `strategy_engine.py` 并重构 `fetch_signal.py` 和前端页面（纯代码重构，解决逻辑分裂）。
2. **重构数据表 (Phase 2)**：重构数据库表结构 `sim_trade_db.py` 并适配 `trade_runner.py`。
3. **统一数据层 (Phase 3)**：抽象 `market_data.py`，并接入涨停板因子。
4. **回测迁移 (Phase 4)**：回测系统迁移至新引擎，验证历史与模拟的完全一致性。

## 7. 性能优化专项（新增 · 2026-04-01）

> 目标：解决“回测特别慢、实时监控也特别慢、页面加载慢”的全链路性能问题。  
> 原则：**先文档对齐，再分阶段改造，再做回测与端到端验收**。

### 7.1 现状瓶颈（基于当前代码）

1. **回测慢（`modules/analyzer.py`）**
   - 串行流程 + 固定 sleep，整体耗时随样本线性膨胀。
   - 指标计算存在 Python 循环，向量化不足。
   - 局部取价语义仍有 `iloc[1]` 风险，且成本扣除需统一参数化。

2. **监控慢（`skills/stock_sim_robot/monitor_intraday.py`）**
   - 持仓逐只串行抓行情，网络超时会放大整轮耗时。
   - 每轮每仓写 `sim_price_log`，写库频率高。
   - 飞书发送同步阻塞，可能拖慢主流程。

3. **页面慢（`pages/sim_trading.py`）**
   - 高频页面存在全量查询倾向，列裁剪/分页不足。
   - 行级格式化与大表渲染计算量高。

4. **存储层慢（`utils/storage.py` + DB）**
   - 上层调用存在全表读取模式。
   - 关键业务表索引不足，查询放大。

### 7.2 优先级改造路线

#### P0（立刻见效）

- `monitor_intraday.py`：行情并发抓取（限并发）+ `sim_price_log` 批量/降频写入。
- `analyzer.py`：移除固定 sleep，改失败退避；修正取价语义；统一交易成本扣除。
- SQL 层：补齐关键索引（`sim_trades/sim_trade_events/sim_price_log/sim_audit_log`）。
- 页面层：默认最近 N 条 + 列裁剪 + 分页，避免首屏全量加载。

#### P1（结构优化）

- 技术指标向量化（rolling/ewm）与回测局部并行化。
- 监控写库批处理标准化。
- 行情缓存策略统一。

#### P2（中长期）

- 增量回测（仅新增日期）。
- 事件驱动监控（阈值接近时提频）。
- 页面局部刷新拆分。

### 7.3 验收指标

1. 回测同区间总耗时下降目标：**≥30%**。
2. 监控单轮耗时稳定低于 cron 周期，不出现轮次叠压。
3. `sim_price_log` 写入量在保证可观测性的前提下降低。
4. 端到端链路一致：Phase A → Phase B → Monitor → 页面展示一致。
