# 龙虎榜动态退出策略——工程化落地方案（v2）

> 本方案在 v1 动态退出策略基础上，结合 A 股最新涨跌停板规则，解决五个实战落地问题：
> API 兜底、查询频率优化、全链路兜底设计、模拟盘实时展示、日志审计体系。

---

## 零、涨跌停板规则适配（2025年最新）

策略的所有参数不能写死为 10%，必须根据股票代码自动匹配正确的涨跌幅限制：

```
板块识别规则（按代码前缀）：

60xxxx / 00xxxx → 主板 → 涨跌幅 ±10%
   └── ST / *ST 主板股 → 2025年6月调整后统一为 ±10%（原5%已废止）
300xxx → 创业板 → 涨跌幅 ±20%
   └── ST / *ST 创业板股 → ±20%
688xxx → 科创板 → 涨跌幅 ±20%
   └── ST / *ST 科创板股 → ±20%
83xxxx / 87xxxx / 88xxxx → 北交所 → 涨跌幅 ±30%

新股特殊规则：
  所有板块新股上市前 5 个交易日不设涨跌幅限制
  盘中设 30% / 60% 两档临时停牌（各 10 分钟）
  停牌跨越 14:57 的，14:57 复牌

价格笼子（连续竞价阶段）：
  买入申报 ≤ 当前最低卖出价 × 102%
  卖出申报 ≥ 当前最高买入价 × 98%
```

### 对策略的影响

原 v1 策略中所有涉及"涨停"的判断必须动态化：

| v1 写法（错误） | v2 写法（正确） |
|---------------|---------------|
| `if 涨幅 >= 10%` 判定涨停 | `if 涨幅 >= get_limit(stock_code)` |
| 连板回撤容忍度固定 5%/7%/8% | 按板块等比缩放，创业板翻倍为 10%/14%/16% |
| 封单比阈值固定 30% | 创业板/科创板因振幅大，封单比阈值提高至 40% |
| 高开 > 7% 放弃 | 创业板改为高开 > 14% 放弃 |

**关键函数签名：**

```python
def get_price_limit(stock_code: str, stock_name: str, ipo_date: str) -> float:
    """
    返回该股票当日的涨跌幅限制比例（小数），如 0.10 / 0.20 / 0.30
    需要判断：代码前缀、是否ST、是否上市未满5日
    """
```

## 一、API 查询的兜底体系

### 1.1 数据源分层架构

不依赖单一数据源，设计三级数据源降级链：

```
┌─────────────────────────────────────────────────┐
│              数据查询请求                          │
├─────────────────────────────────────────────────┤
│                                                   │
│  Level 1（主源）                                   │
│  ├── 实时行情：券商行情 API（QMT / PTrade）         │
│  ├── 量比数据：券商 Level-2 数据接口                │
│  ├── 特点：最快、最稳、有 SLA 保障                  │
│  ├── 超时阈值：2 秒                                │
│  └── 失败 → 降级到 Level 2                         │
│                                                   │
│  Level 2（备源）                                   │
│  ├── 实时行情：AKShare stock_zh_a_spot_em()        │
│  ├── 量比数据：AKShare + 自算                      │
│  ├── 特点：免费、可用性 ~95%，偶有限流               │
│  ├── 超时阈值：5 秒                                │
│  └── 失败 → 降级到 Level 3                         │
│                                                   │
│  Level 3（兜底源）                                  │
│  ├── 实时行情：新浪财经 HTTP 接口（hq.sinajs.cn）   │
│  ├── 量比数据：不可用，使用缓存值                    │
│  ├── 特点：简单稳定、但数据字段有限                  │
│  ├── 超时阈值：5 秒                                │
│  └── 失败 → 进入"数据断流"模式                      │
│                                                   │
│  数据断流模式                                       │
│  ├── 使用最后一次成功获取的价格（缓存）              │
│  ├── 标记为"陈旧数据"，UI 上用黄色警告显示           │
│  ├── 如果连续 3 分钟无法获取任何数据：               │
│  │   → 触发紧急告警（电话通知）                      │
│  │   → 所有持仓执行"保守清仓"（挂卖一价卖出）        │
│  └── 日志记录断流时长和恢复时间                      │
│                                                   │
└─────────────────────────────────────────────────┘
```

### 1.2 量比接口的专项兜底

量比是动能评分（MS）中权重最高的因子（40%），它的缺失对策略影响最大。

**量比的本质：** `量比 = 当前累计成交量 / (过去5日平均每分钟成交量 × 当日已开盘分钟数)`

即使接口不返回量比字段，也可以用两个基础数据自行计算：

```
自算量比的数据需求：
  ① 当前累计成交量（几乎所有行情接口都有）
  ② 过去 5 日每日总成交量（本地数据库缓存，每天收盘更新一次）

自算公式：
  past_5d_avg_vol = sum(近5日每日成交量) / 5
  avg_per_minute = past_5d_avg_vol / 240  （每天 240 分钟交易时间）
  elapsed_minutes = (当前时间 - 09:30) 的分钟数，午休时间扣除
  量比 = 当前累计成交量 / (avg_per_minute × elapsed_minutes)
```

**兜底方案完整链路：**

```
量比获取流程：

① 尝试从 Level 1 接口获取量比字段
   ├── 成功 → 使用，并缓存到 last_known_volume_ratio
   └── 失败 ↓

② 尝试从任意接口获取"当前成交量"，用本地缓存的5日均量自算
   ├── 成功 → 使用自算值，日志标记 [VOLUME_RATIO_CALCULATED]
   └── 失败 ↓

③ 使用 last_known_volume_ratio 缓存值
   ├── 缓存时间 < 5分钟 → 直接使用，日志标记 [VOLUME_RATIO_CACHED_FRESH]
   ├── 缓存时间 5~15分钟 → 使用但降权（MS 中量能维度权重从40%降为20%）
   │   日志标记 [VOLUME_RATIO_CACHED_STALE]
   └── 缓存时间 > 15分钟 → 量能维度得分强制设为50（中性值）
       日志标记 [VOLUME_RATIO_UNAVAILABLE]
       触发 WARNING 告警
```

### 1.3 封单数据的兜底

封单数据（涨停时的排队买单量）只有 Level-2 接口才有，普通行情看不到。

```
封单数据兜底：

Level 1（有 Level-2 数据）：
  直接获取 买一挂单量 / 卖一挂单量

Level 2（无 Level-2 数据时的替代判断）：
  用以下信号间接评估封板强度：
  ① 涨停后是否有成交（无成交 = 封得死）
  ② 涨停时间（越早封板越强）
  ③ 涨停后的成交量变化（封板后成交量骤降 = 封单厚）

兜底评分：
  无法获取封单数据时，封板强度默认设为"中等"
  但如果涨停后出现过一次开板，则强制设为"弱"
```

### 1.4 接口调用的异常处理规范

所有 API 调用必须遵循以下规范：

```
每次 API 调用的标准流程：

1. 记录请求开始时间 t_start
2. 设置超时（Level 1: 2秒, Level 2: 5秒, Level 3: 5秒）
3. 捕获以下异常类型：
   - ConnectionError → 网络不通，切下一级数据源
   - Timeout → 超时，切下一级数据源
   - HTTPError 429 → 被限流，等待 2 秒后重试 1 次，仍失败则切下一级
   - HTTPError 5xx → 服务端故障，切下一级数据源
   - JSONDecodeError → 返回数据格式错误，切下一级
   - KeyError / IndexError → 返回字段缺失，用默认值补位
4. 记录请求结束时间 t_end
5. 计算耗时 = t_end - t_start
6. 写入日志：
   [时间] [数据源等级] [接口名] [股票代码] [耗时ms] [状态:成功/失败/降级]
   [失败时附加: 异常类型, 异常信息]
7. 更新接口健康度统计：
   - 维护每个接口最近 100 次调用的成功率
   - 如果某接口成功率 < 80%，发 WARNING 告警
   - 如果某接口成功率 < 50%，自动跳过该接口直接用下一级
```

## 二、查询频率优化

### 2.1 分时段差异化查询频率

**核心原则：** 盘中不同时段的波动剧烈程度不同，查询频率应与潜在风险成正比。不能所有时段都用同一频率——既浪费资源又在关键时刻不够及时。

```
┌───────────────────────────────────────────────────────────────┐
│                    查询频率分配方案                               │
├──────────────────┬────────────┬────────────────────────────────┤
│ 时段              │ 查询间隔    │ 原因                           │
├──────────────────┼────────────┼────────────────────────────────┤
│ 09:15 ~ 09:25    │ 10 秒      │ 集合竞价，决定是否执行买入计划    │
│ （集合竞价）       │            │ 高开幅度直接决定操作模式         │
├──────────────────┼────────────┼────────────────────────────────┤
│ 09:25 ~ 09:30    │ 不查询      │ 盘前静默期，无法交易             │
├──────────────────┼────────────┼────────────────────────────────┤
│ 09:30 ~ 09:45    │ 30 秒 ★    │ 开盘后前15分钟是全天最关键时段   │
│ （黄金15分钟）     │            │ 高开低走的识别窗口               │
│                   │            │ 必须高频监控才能及时止盈          │
├──────────────────┼────────────┼────────────────────────────────┤
│ 09:45 ~ 10:30    │ 1 分钟      │ 第二关键时段，趋势初步确立       │
│ （早盘确认期）     │            │ 30秒略快但可接受                 │
├──────────────────┼────────────┼────────────────────────────────┤
│ 10:30 ~ 11:30    │ 2 分钟      │ 盘中平稳期，波动相对较小         │
│ （上午平稳期）     │            │ 但如果持仓浮亏接近止损线         │
│                   │            │ 自动切回 30 秒频率               │
├──────────────────┼────────────┼────────────────────────────────┤
│ 11:30 ~ 13:00    │ 不查询      │ 午间休市                        │
├──────────────────┼────────────┼────────────────────────────────┤
│ 13:00 ~ 13:15    │ 1 分钟      │ 午后开盘，注意跳水或拉升         │
├──────────────────┼────────────┼────────────────────────────────┤
│ 13:15 ~ 14:30    │ 2 分钟      │ 下午平稳期                      │
├──────────────────┼────────────┼────────────────────────────────┤
│ 14:30 ~ 14:57    │ 30 秒 ★    │ 尾盘决策期，决定是否持仓过夜     │
│ （尾盘关键期）     │            │ 尾盘拉升/跳水频发                │
├──────────────────┼────────────┼────────────────────────────────┤
│ 14:57 ~ 15:00    │ 不主动查询  │ 收盘集合竞价，此时不建议交易     │
│ （收盘集合竞价）   │            │ 流动性差，滑点大                 │
└──────────────────┴────────────┴────────────────────────────────┘
```

### 2.2 事件驱动的动态加速

在上述基础频率之上，当特定条件触发时，自动提高查询频率：

```
动态加速规则：

触发条件 → 临时查询间隔 → 持续时长

① 浮亏接近止损线（距止损 < 1%）
   → 切为 15 秒
   → 直到脱离危险区（浮亏回到止损线上方 2%）

② 股价触及涨停价
   → 切为 15 秒
   → 用于监控封单稳固性，直到确认封死（5分钟内无开板）

③ 确认高开低走模式启动
   → 切为 15 秒
   → 直到该股票减仓操作完成

④ MS 分数从 ≥60 骤降至 <40（动能急剧衰减）
   → 切为 15 秒
   → 直到完成清仓或 MS 恢复至 ≥50

⑤ 大盘指数（上证/深证）5分钟内跌幅 > 1%
   → 所有持仓股全部切为 30 秒
   → 持续 15 分钟，或直到大盘企稳
```

### 2.3 查询资源预算与限流保护

```
资源预算计算（以持仓 3 只股票为例）：

常规时段（2分钟间隔）：
  每只股 30 次/小时 × 3 只 = 90 次/小时

关键时段（30秒间隔，每天约1.5小时）：
  每只股 120 次/小时 × 3 只 × 1.5 小时 = 540 次

全天总调用量预估：
  常规：90 × 2.5 小时 = 225 次
  关键：540 次
  动态加速预留：~200 次
  合计：约 1000 次/天/数据源

AKShare 的经验限流阈值：约 300~500 次/小时
→ 结论：AKShare 作为备源可以支撑，但关键时段需要主源（券商API）兜底
```

### 2.4 最少与最优查询频率总结

| 维度 | 最少频率（勉强可用） | 最优频率（推荐） | 说明 |
|------|---------------------|-----------------|------|
| 集合竞价 | 25秒 1次 | 10秒 1次 | 集合竞价只有 10 分钟，需快速判断 |
| 黄金15分钟 | 1分钟 1次 | 30秒 1次 | 高开低走必须在 3~5 根K线内识别 |
| 常规时段 | 3分钟 1次 | 2分钟 1次 | 太慢会错过急跌，太快浪费资源 |
| 尾盘决策期 | 1分钟 1次 | 30秒 1次 | 14:30后走势对次日高度相关 |
| 危险区间 | 30秒 1次 | 15秒 1次 | 接近止损线时必须高频 |

**绝对底线：** 任何时段的查询间隔不得超过 3 分钟。超过 3 分钟意味着如果股票闪崩（如从+5%瞬间跌至-3%），你可能完全错过止损窗口。

## 三、全链路兜底设计

### 3.1 兜底分级体系

将所有可能出错的环节按严重程度分为四级，每级有明确的兜底措施：

```
┌─────────────────────────────────────────────────────────────┐
│                     兜底分级体系                               │
├─────────┬────────────────────┬──────────────────────────────┤
│ 级别     │ 故障场景            │ 兜底措施                      │
├─────────┼────────────────────┼──────────────────────────────┤
│         │ 单个接口超时         │ 切备用数据源，无感知           │
│ G1      │ 单个字段缺失         │ 用缓存值或默认值补位          │
│ 可自愈   │ 单次计算异常         │ 用上一次的 MS 分数            │
│         │ 非关键日志写入失败   │ 写入内存缓冲区稍后重试         │
├─────────┼────────────────────┼──────────────────────────────┤
│         │ 主备数据源都失败     │ 使用 Level 3 新浪接口         │
│ G2      │ 量比/封单完全不可用  │ 对应维度用中性分数 50 替代    │
│ 需关注   │ 数据库写入失败       │ 写本地 CSV 文件作为冗余       │
│         │ 计算结果明显异常     │ 丢弃本次结果，发 WARNING      │
├─────────┼────────────────────┼──────────────────────────────┤
│         │ 所有数据源断流>1分钟 │ UI 显示"数据延迟"黄色警告     │
│ G3      │ 下单接口报错         │ 重试2次，仍失败则人工介入提醒  │
│ 需干预   │ 策略进程 CPU>90%    │ 降低查询频率至最低档          │
│         │ 磁盘空间不足         │ 停止写详细日志，只写关键日志   │
├─────────┼────────────────────┼──────────────────────────────┤
│         │ 所有数据源断流>3分钟 │ 触发保守清仓（全部持仓挂卖）  │
│ G4      │ 策略进程崩溃         │ 看门狗进程自动重启 + 电话告警  │
│ 紧急     │ 账户异常（余额对不上）│ 立即停止所有交易 + 电话告警   │
│         │ 网络完全中断         │ 通过手机 APP 手动处理持仓     │
└─────────┴────────────────────┴──────────────────────────────┘
```

### 3.2 动能评分（MS）的兜底计算

当某个维度的数据完全不可用时，MS 的计算方式需要降级：

```
MS 降级计算规则：

正常模式（所有数据可用）：
  MS = V_score × 0.40 + P_score × 0.35 + B_score × 0.25

量能维度缺失（V_score 不可用）：
  V_score 强制设为 50
  MS = 50 × 0.40 + P_score × 0.54 + B_score × 0.39
  （重新归一化剩余维度的权重）
  日志标记 [MS_DEGRADED_NO_VOLUME]

盘口维度缺失（B_score 不可用，无 Level-2 数据）：
  B_score 强制设为 50
  MS = V_score × 0.53 + P_score × 0.47
  日志标记 [MS_DEGRADED_NO_L2]

仅价格可用（V_score 和 B_score 都不可用）：
  MS 完全由价格结构决定
  MS = P_score
  但此时 MS 的可信度很低：
  → 所有减仓/清仓阈值上移 10 分（更保守）
  → 即 MS < 50 就清仓（正常是 < 40）
  日志标记 [MS_DEGRADED_PRICE_ONLY]
  触发 WARNING 告警

所有维度都不可用（完全断流）：
  MS 不可计算
  → 进入 G4 紧急模式，准备保守清仓
  日志标记 [MS_UNAVAILABLE]
  触发 CRITICAL 告警
```

### 3.3 交易执行的兜底

```
下单失败的处理流程：

1. 第一次下单失败：
   等待 1 秒，重试一次
   
2. 第二次仍失败：
   等待 3 秒，换一种报价方式重试
   （如从限价单改为市价单）

3. 第三次仍失败：
   发送 CRITICAL 告警
   记录"未成交订单"到 pending_orders 表
   UI 上闪红色警告："下单失败，请手动处理"
   策略暂停下新单，但继续监控已有持仓

4. 涨停/跌停无法成交的处理：
   涨停封死买不进 → 放弃该标的，日志记录"涨停未买入"
   跌停封死卖不出 → 挂跌停价排队，次日开盘优先卖出
                    日志记录"跌停排队卖出"
                    次日开盘第一个动作就是检查该股是否成交
```

### 3.4 看门狗进程

策略主进程之外，单独运行一个看门狗进程：

```
看门狗职责：

1. 心跳检测：每 30 秒检查策略主进程是否存活
   → 如果连续 3 次（90秒）无心跳 → 重启主进程 + CRITICAL 告警

2. 资源监控：每分钟检查 CPU / 内存 / 磁盘
   → CPU > 90% 持续 5 分钟 → WARNING 告警
   → 磁盘剩余 < 1GB → WARNING 告警 + 触发日志清理

3. 交易时段守卫：
   → 确保主进程在 09:10 之前启动
   → 确保主进程在 15:10 之后还在运行（处理收盘后逻辑）

4. 数据一致性校验：
   → 每天 15:30 对比"策略记录的持仓"与"券商系统实际持仓"

### 4.2 "预计卖出价"的计算逻辑

UI 上显示的"预计卖出价"不是随意估计，而是根据当前状态精确计算：

```
预计卖出价的计算规则：

场景 A：MS ≥ 60（继续持有）
  显示文字："✅ 继续持有"
  同时显示移动止盈线价格（这就是最坏情况下的卖出价）
  预计卖出价 = 移动止盈线 = Highest_Close - K × ATR(5)

场景 B：MS 40~59（准备减仓）
  预计卖出价 = 当前价格（因为即将执行市价卖出）
  显示文字："⚠️ 准备减仓50%，预计卖出价 ≈ {当前价}"

场景 C：高开低走模式
  预计卖出价 = 当前 VWAP（跌破 VWAP 时的卖出价）
  显示文字："⚠️ 高开低走，预计卖出价 ≈ {VWAP}"

场景 D：涨停封板
  显示文字："🔒 涨停封板中，不卖出"
  附注："若开板 → 卖出价 = 开板瞬间价格"

场景 E：触及止损区
  预计卖出价 = 止损价
  显示文字："🔴 接近止损！预计卖出价 = {止损价}"

场景 F：数据不可用
  显示文字："⚪ 数据延迟，最后已知价 {缓存价格}（{缓存时间}前）"
  背景变为黄色
```

### 4.3 UI 刷新机制

```
UI 刷新 与 数据查询 解耦设计：

数据层：后台线程按 2.1 节的频率查询数据，结果写入共享内存/队列
展示层：UI 固定每 1 秒刷新一次显示内容（从共享内存读取最新数据）

好处：
  - 即使数据查询有延迟，UI 不会卡住
  - UI 刷新频率高（1秒），用户体验流畅
  - 数据查询频率按需调整，不受 UI 限制

需要在 UI 上显示的"倒计时"：
  "下次查询: 10:23:42 (18秒后)"
  让用户知道数据的新鲜度

数据状态指示灯：
  🟢 正常：最近一次查询成功且在预期时间内
  🟡 延迟：最近一次查询成功但距今 > 预期间隔的 2 倍
  🔴 断流：最近 3 次查询全部失败
```

### 5.2 各日志的内容格式

#### strategy.log（策略决策日志）——按天写入

这是最核心的日志，记录每一次决策的完整上下文。用于事后复盘和策略优化。

```
格式（每条一个 JSON 行）：

{
  "ts": "2026-03-31T10:23:12.345",        // 毫秒级时间戳
  "event": "MS_CALCULATED",                // 事件类型
  "stock": "002594",                        // 股票代码
  "stock_name": "比亚迪",                   // 股票名称
  "board": "创业板",                        // 所属板块
  "price_limit": 0.20,                     // 涨跌幅限制
  "current_price": 293.55,                 // 当前价格
  "buy_price": 285.00,                     // 买入价
  "pnl_pct": 0.030,                        // 当前浮盈百分比
  "position_ratio": 0.25,                  // 仓位占比
  
  "ms_score": 72,                          // 动能综合评分
  "ms_detail": {                           // 各维度明细
    "volume_score": 68,
    "volume_source": "CALCULATED",          // 量能来源：API/CALCULATED/CACHED
    "price_score": 78,
    "orderbook_score": 65,
    "orderbook_source": "L2_API"
  },
  
  "trailing_stop": 286.84,                 // 当前移动止盈线
  "stop_loss": 276.45,                     // 当前止损线
  "atr5": 4.23,                            // 5日ATR
  
  "decision": "HOLD",                      // 决策：HOLD / SELL_HALF / SELL_ALL / ACCELERATE
  "decision_reason": "MS>=60, price above trailing stop",
  
  "data_quality": {                        // 数据质量标记
    "data_source_level": 1,
    "data_freshness_ms": 345,
    "degraded_factors": []                  // 降级的因子列表
  }
}
```

**事件类型枚举：**

| event 值 | 含义 | 频率 |
|---------|------|------|
| `MS_CALCULATED` | 完成一次动能评分计算 | 每次查询 |
| `DECISION_HOLD` | 决策：继续持有 | 每次查询（结果为持有时） |
| `DECISION_SELL` | 决策：卖出（含减仓） | 触发卖出时 |
| `TRAILING_STOP_UPDATED` | 移动止盈线更新（上移） | 价格创新高时 |
| `MODE_SWITCH` | 模式切换（如进入高开低走模式） | 触发时 |
| `LIMIT_UP_DETECTED` | 检测到涨停 | 触发时 |
| `LIMIT_UP_OPENED` | 涨停板打开 | 触发时 |
| `FREQUENCY_CHANGED` | 查询频率切换 | 频率变化时 |
| `DATA_DEGRADED` | 数据降级 | 降级时 |
| `DATA_RECOVERED` | 数据恢复 | 恢复时 |

#### price_ticks_{HH}.log（价格流水日志）——按小时写入

高频记录每次查询获取的原始价格数据，用于事后精确复盘和策略参数优化。

```
格式（紧凑 CSV，每行一条记录，极致省空间）：

ts,stock,price,open,high,low,vol,vol_ratio,vwap,bid1,ask1,data_src,latency_ms
10:23:12.345,002594,293.55,289.00,294.20,288.50,1523400,1.85,291.30,293.50,293.55,L1,85

  vol_ratio = 量比
  vwap = 分时均价

```

**为什么按小时分文件：** 以 3 只持仓股、平均 1 分钟查询 1 次计算，每小时约 180 条记录，单文件约 30KB。按天合并则约 100KB，完全可控。但按小时分文件的好处是：复盘某个时段的走势时可以快速定位文件，而不用在全天日志中搜索。

  永久保留（至少 3 年，建议 5 年）
  按年份压缩归档

alerts/ 目录下的告警日志：
  保留 1 年

数据库：
  positions 表：只保留当前持仓，卖出后转移到 trade_history
  ms_snapshots 表：保留最近 60 个交易日的明细，超期聚合为日均值
  daily_summary 表：永久保留
  api_health 表：保留最近 90 天

磁盘空间预估（3只持仓，每日）：
  price_ticks: ~300KB/天
  strategy.log: ~500KB/天
  trades.log: ~5KB/天
  其他日志: ~50KB/天
  数据库增量: ~200KB/天
  合计: ~1MB/天 → 一年约 250MB，完全可控
```

### 5.5 日志查询的常见场景

以下是复盘时最常用的查询模式：

```
场景 1："为什么这笔交易亏了？"

  → 查 trades.log 找到该笔交易的 trade_id 和 trigger_reason
  → 用 trade_id 关联 strategy.log 找到触发前后的 MS 变化过程
  → 用时间范围查 price_ticks 看当时的价格走势细节

场景 2："这个参数调整后效果如何？"

  → 查 daily_summary 表对比参数调整前后的胜率和收益率
  → 查 ms_snapshots 表统计各 MS 区间的实际后续收益

场景 3："今天为什么一笔交易都没做？"

  → 查 strategy.log 中的 market_temp 相关日志
  → 查 api_health 确认不是因为数据断流导致

场景 4："API 最近是否不稳定？"

  → 查 api_health 表，按天统计各数据源的成功率趋势
  → 如果 Level 1 成功率下降，提前联系券商排查

场景 5："对账——策略记录和实际成交是否一致？"

  → 导出 audit.log 与券商交割单逐笔比对
  → 关注 slippage 和 actual_price 与 planned_price 的偏差
```
