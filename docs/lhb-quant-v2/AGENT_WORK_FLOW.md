# Agent 辅助开发量化系统 - 工作流指南

> 本文档定义了使用 CodeFlicker Agent 分模块开发的推荐工作流

---

## 一、工作流概述

### 1.1 核心原则

```
不推荐：                           推荐：
┌─────────────────┐               ┌──────────┐ ┌──────────┐ ┌──────────┐
│  窗口1：前端    │               │ 会话1    │ │ 会话2    │ │ 会话3    │
│  所有前端代码   │               │ 数据层   │ │ 策略+交易│ │ API层    │
└─────────────────┘               └──────────┘ └──────────┘ └──────────┘
问题：上下文爆炸，           ┌──────────┐
输出质量下降                 │ 会话4    │
                             │ 前端     │
                             └──────────┘
```

**关键原则**：
- 按功能模块分会话，而非按技术栈分
- 每个会话有明确的角色和边界
- 会话之间通过接口签名和数据格式传递约定
- 先各自开发再集成

### 1.2 会话划分

| 会话 | 模块 | 负责内容 |
|------|------|----------|
| 会话1 | 数据层 | ORM模型、数据采集、降级链、迁移 |
| 会话2 | 策略+交易 | 评分引擎、选股服务、交易执行、风控 |
| 会话3 | API层 | FastAPI路由、WebSocket、中间件 |
| 会话4 | 前端 | Vue3页面、组件、状态管理 |
| 会话5 | 基础设施 | Docker、CI/CD、Makefile |
| 会话6 | 测试 | 单元测试、集成测试、E2E |

### 1.3 依赖关系

```
会话1（数据层）
  ↓ 输出：ORM 模型、数据采集接口
会话2（策略+交易）
  ↓ 输出：Service 类方法签名、业务逻辑
会话3（API 层）
  ↓ 输出：接口定义、Pydantic 模型
会话4（前端）
```

## 三、开发顺序

### Phase 1: 基础设施并行

```
┌─────────────────────────────────────┐
│ 会话5: 基础设施                     │
│ - Docker Compose 配置               │
│ - 目录结构创建                      │
│ - Makefile 编写                     │
│ - 环境变量模板                      │
└─────────────────────────────────────┘
```

### Phase 2: 数据层 + API层 并行

```
┌─────────────────────┐ ┌─────────────────────┐
│ 会话1: 数据层        │ │ 会话3: API层        │
│ - ORM 模型          │ │ - Pydantic Schema   │
│ - 数据采集服务      │ │ - FastAPI 路由骨架  │
│ - Alembic 迁移      │ │ - WebSocket 协议    │
└─────────────────────┘ └─────────────────────┘
```

### Phase 3: 策略+交易

```
┌─────────────────────────────────────┐
│ 会话2: 策略与交易引擎                 │
│ - 评分引擎                          │
│ - 选股服务                          │
│ - 交易执行                          │
│ - 风控服务                          │
│ 依赖：会话1 的 ORM 模型              │
└─────────────────────────────────────┘
```

### Phase 4: 前端

```
┌─────────────────────────────────────┐
│ 会话4: 前端开发                      │
│ - 页面框架                          │
│ - API 集成                          │
│ - WebSocket 集成                    │
│ 依赖：会话3 的 API 接口              │
└─────────────────────────────────────┘
```

### Phase 5: 测试与集成

```
┌─────────────────────────────────────┐
│ 会话6: 测试                          │
│ - 单元测试                          │
│ - 集成测试                          │
│ - E2E 测试                          │
│ 依赖：所有模块完成                   │
└─────────────────────────────────────┘
```

## 四、Prompt 使用方法

### 4.1 创建新会话

在 CodeFlicker 中创建新会话时：

1. 选择对应的会话 Prompt 文档（如 `S01_DATA_LAYER.md`）
2. 将完整内容复制到新会话的 System Prompt
3. 根据当前开发阶段，可能需要补充：
   - 相关设计文档的引用
   - 已完成模块的代码
   - 具体的开发任务

### 4.2 会话衔接

每个会话完成后：

1. **记录接口约定**：
   - Service 类的方法签名
   - 数据模型的结构
   - API 端点的格式

2. **传递到下一会话**：
   - 将关键代码复制到下一会话的 Prompt
   - 更新下一会话的依赖说明

### 4.3 集成问题处理

当各模块开发完成后，创建集成会话处理：

1. 合并所有模块代码
2. 解决接口不匹配问题
3. 端到端测试
4. 修复发现的问题

## 五、评审检查点

在每个会话开发的关键节点进行评审：

### 会话1 完成后
- [ ] ORM 模型是否完整
- [ ] Alembic 迁移脚本是否可执行
- [ ] 数据采集服务是否有降级链
- [ ] 是否符合 `DATABASE.md` 设计

### 会话2 完成后
- [ ] 评分引擎是否符合 `STRATEGY.md`
- [ ] 风控服务是否符合 `RISK_CONTROL.md`
- [ ] 交易流程是否符合 `TRADING_FLOW.md`
- [ ] 状态机是否符合 `STATE_MACHINE.md`

### 会话3 完成后
- [ ] API 是否符合 `API.md` 设计
- [ ] Pydantic Schema 是否完整
- [ ] WebSocket 协议是否完善

### 会话4 完成后
- [ ] 页面是否覆盖所有功能
- [ ] WebSocket 实时数据是否正确
- [ ] 错误处理是否完善

## 六、版本控制

每个会话的开发建议单独提交：

```bash
git add backend/app/models
git commit -m "feat(data): 完成 ORM 模型定义

- 新增 robots, robot_trades, strategies 等模型
- 添加 Alembic 初始迁移脚本
- 更新 README"

git add backend/app/services
git commit -m "feat(trading): 完成评分引擎和交易服务

- 实现多因子评分计算
- 实现 Phase A/B 交易流程
- 实现 AHS 风控服务"

git add backend/app/api
git commit -m "feat(api): 完成 FastAPI 路由

- 新增 robots, market, selection 等端点
- 实现 WebSocket 实时推送
- 添加 Pydantic Schema"
```
