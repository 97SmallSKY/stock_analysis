# 龙虎榜量化交易系统 v2 - 架构评审报告

> 评审日期: 2026-04-16
> 评审范围: 技术架构、调度层、数据源、交易执行、WebSocket、API、部署、运维

---

## 一、调度与任务层

### 1.1 APScheduler 嵌入 FastAPI 进程（高风险） ⚠️ P0

**问题：**
- APScheduler 运行在 FastAPI 进程内部，FastAPI 重启/崩溃时所有调度任务丢失
- 盘中10秒监控是最关键路径（止盈止损），与 Web 请求共享进程资源，高并发时可能互相影响
- 多 Worker 部署（uvicorn --workers 4）时，APScheduler 会在每个 Worker 中各执行一次，导致重复选股、重复买卖

**优化方案：**
- 将调度器拆为独立进程/容器，与 FastAPI 解耦
- 用 Celery Beat 替代 APScheduler 做定时触发，Celery Worker 做实际执行
- 盘中监控使用独立队列，与回测、数据同步等慢任务隔离
- 所有关键调度任务加分布式锁，防止重复执行

### 1.2 APScheduler 与 Celery 职责边界不清

**问题：**
- 两套调度系统并存，APScheduler 负责定时触发，Celery 负责异步执行，但文档中未明确哪些任务走哪条链路
- 运维需要同时监控两套系统的健康状态，复杂度翻倍

**优化方案：**
- **统一为一套：Celery Beat 调度 + Celery Worker 执行**
- 如果坚持用 APScheduler，必须独立进程部署，使用 Redis JobStore 做持久化，触发后通过 Celery 异步执行

### 1.3 盘中10秒监控缺乏容错机制

**问题：**
- 数据源超时或异常时的处理策略未定义——如果行情数据拿不到，是跳过还是用缓存？
- 连续多次获取不到行情的紧急处理方案缺失（可能错过止损窗口）
- 10秒一次轮询，如果单次执行超过10秒会导致任务堆积
- 没有监控执行耗时的指标上报

**优化方案：**
- 定义数据源超时时间（如3秒），超时后降级到缓存/上一笔报价
- 设置连续失败阈值，达到后暂停新开仓并发告警
- 单次执行加超时控制，超过8秒强制结束并告警
- 每个监控周期上报耗时、检查数、触发数、错误数等指标

## 二、数据源与数据可靠性

### 2.1 数据源降级链缺乏细粒度设计

**问题：**
- 当前降级链是 TuShare → AKShare → Sina → Crawler，但不同类型的数据（日K、实时行情、龙虎榜）适用的数据源不同，不应共用一条降级链
- 熔断器的参数（失败率阈值、滑动窗口大小、恢复探测间隔）未定义
- 降级切换时没有数据格式校验——不同源返回的字段名、精度、单位可能不一致

**优化方案：**
- **按数据类型分别配置降级链**
  - DAILY_KLINE: TuShare → AKShare → Crawler
  - LHB_DETAIL: AKShare → Crawler
  - REALTIME_QUOTE: AKShare → Sina → WebSocket
- 明确熔断参数：如30秒内失败率>50%触发熔断，60秒后半开探测
- 每个数据源返回数据后做标准化校验，确保字段一致性
- 降级切换事件写入日志并推送告警

### 2.2 行情数据的时效性和一致性

**问题：**
- 实时行情是轮询模式（10秒一次），存在最多10秒的延迟，对快速跌停场景可能来不及止损
- 多只股票的行情是逐个获取还是批量获取未定义——逐个获取在持仓多时延迟会线性增长
- Redis 缓存的行情数据和数据库的快照之间可能存在不一致

**优化方案：**
- **行情获取必须批量请求**，不能逐只轮询
- 评估是否需要 WebSocket 推送行情替代轮询，至少在持仓较多时切换
- 明确 Redis 行情缓存的 TTL 和更新策略，**过期数据必须标记**而非静默使用

## 三、交易执行与风控

### 3.1 Phase A/B 两阶段执行的异常处理缺失

**问题：**
- Phase A（18:50 选股+模拟买入）到 Phase B（09:35 确认买入）之间跨越一个晚上，期间可能发生：停牌、ST、重大利空公告、集合竞价异常等
- Phase B 确认买入时的价格与 Phase A 的预期价格可能偏差很大，没有偏离度保护
- 如果 Phase A 执行成功但 Phase B 因故未执行（进程崩溃、网络问题），持仓状态会处于不一致状态

**优化方案：**
- **Phase B 执行前增加前置检查**：停牌检测、ST 检测、集合竞价价格偏离度检查
- 定义价格偏离保护阈值，如开盘价与预期价偏离超过 N% 则放弃买入
- **增加状态恢复机制**：Phase B 启动时检查是否有未完成的 Phase A 记录，处理残留状态
- **Phase A 的选股结果应持久化到数据库**而非仅在内存中，保证跨进程可恢复

### 3.2 分档止盈止损的并发安全

**问题：**
- 10秒监控中如果同时触发 sell1 和 sell2（价格快速上涨），是否会重复卖出
- 止损和止盈的判断与执行之间如果有延迟，价格可能已经变化，导致实际执行价格与决策价格不一致
- 多个机器人持有同一只股票时，同时触发卖出是否会互相干扰

**优化方案：**
- **每笔交易的卖出操作加乐观锁或悲观锁**，确保不会重复卖出
- 记录决策价格和实际执行价格的偏差（滑点追踪），用于后续优化
- **多机器人并发操作时在交易执行层面加股票级锁**

### 3.3 AHS 风控的触发时机问题

**问题：**
- AHS 评分仅在 Phase A 选股时检查，盘中不检查——如果盘中市场急剧恶化，已持仓的股票没有额外保护
- AHS 的输入数据（胜率、连亏次数等）更新频率未定义，如果只在收盘后更新，盘中的风控是滞后的
- AHS 评分阈值（0-20-40-60-80-100）是硬编码还是可配置未明确

**优化方案：**
- **盘中增加市场情绪的实时检查**，大盘急跌时触发全局风控（如暂停所有新开仓、收紧止损线）
- **AHS 的计算参数和阈值应放入 strategy_params 或 app_config**，支持运行时调整
- 增加组合层面的风控：单日最大亏损额、最大持仓集中度等

## 四、WebSocket 与实时推送

### 4.1 WebSocket 缺乏设计细节

**问题：**
- 三个 WebSocket 端点（quotes/pnl/orders）的推送频率、消息格式、背压策略都未定义
- WebSocket 连接断开后的重连策略未设计（前端）
- 如果前端无人连接，后端是否还会持续计算推送数据——资源浪费

**优化方案：**
- 定义每个 WebSocket 通道的推送频率（如 quotes 每秒一次、pnl 每10秒一次、orders 仅事件触发）
- 定义消息格式规范（包含时间戳、序列号，用于检测丢失和乱序）
- **后端使用发布/订阅模式**，无订阅者时不产生计算
- 前端实现指数退避重连 + 心跳检测

### 4.2 Nginx 代理 WebSocket 的配置风险

**问题：**
- Nginx 默认的 proxy_read_timeout 是 60 秒，长时间无消息的 WebSocket 会被断开
- WebSocket 连接数量没有限制，可能耗尽后端资源

**优化方案：**
- Nginx 配置中增加 WebSocket 专用超时和心跳配置
- 后端限制单用户最大 WebSocket 连接数
- 考虑 WebSocket 连接的健康检查和优雅断开

## 五、API 设计

### 5.1 API 版本管理和错误规范缺失

**问题：**
- 虽然有 /api/v1/ 前缀，但没有定义版本演进策略和向后兼容承诺
- 统一的错误响应格式未定义——前端不知道如何统一处理错误
- 缺少分页、排序、过滤的通用规范

**优化方案：**
- **定义统一响应格式**：`{ code, message, data, timestamp }`
- **定义统一错误码体系**（业务错误码 vs HTTP 状态码）
- 制定分页规范：如 `?page=1&size=20` 或 cursor 分页，响应中包含 total/has_next
- 批量查询接口加最大返回条数限制，防止一次拉取全量数据

### 5.2 回测接口缺乏任务管理

**问题：**
- 只有 POST /backtest/run 和 GET /backtest/{task_id}，缺少任务列表、取消任务、删除历史结果等
- 回测可能耗时很长，前端如何感知进度未设计
- 多人同时提交回测时的资源竞争未考虑

**优化方案：**
- 补充接口：任务列表、取消、进度查询
- 回测任务通过 WebSocket 或轮询推送进度百分比
- 限制同时运行的回测任务数量，超出排队

### 5.3 缺少幂等性设计

**问题：**
- POST /robots（创建机器人）、POST /data/sync（数据同步）等写接口没有幂等性保证
- 网络超时重试可能导致重复创建

**优化方案：**
- 关键写接口支持幂等键（如请求头 X-Idempotency-Key）
- 数据同步接口天然应该幂等（UPSERT 语义）

## 六、部署与运维

### 6.1 单机部署的可用性风险

**问题：**
- 生产环境仍然是单机部署，PostgreSQL 和 Redis 都是单实例，任何一个组件挂掉系统全停
- 交易系统的停机直接意味着无法执行止损，会造成资金损失

**优化方案：**
- 数据库至少做主从复制，从库用于读查询和灾备
- Redis 使用 Sentinel 或至少开启 AOF 持久化
- 关键进程（监控、交易执行）增加 watchdog 自动拉起
- 定义 RTO（恢复时间目标）和 RPO（数据恢复点目标），至少做到分钟级恢复

### 6.2 缺少蓝绿/灰度发布策略

**问题：**
- 交易系统不能随意停机更新——正在持仓时更新代码可能导致状态不一致
- 策略参数变更的生效方式未定义（立即生效？下一交易日生效？）

**优化方案：**
- **非交易时段（15:00-09:00）做发布窗口**
- **策略参数变更增加生效时间字段**，支持"下一交易日生效"
- 数据库迁移必须向后兼容，支持新旧代码同时运行

### 6.3 备份策略缺失

**问题：**
- 交易数据、持仓状态、净值记录等都是不可重建的关键数据，没有备份方案

**优化方案：**
- PostgreSQL 每日全量备份 + WAL 归档实现增量备份
- 交易状态表（robots、robot_trades）每次变更写审计日志，可回溯
- 备份定期恢复验证

## 七、可观测性

### 7.1 监控体系过于简单

**问题：**
- 只有 loguru 日志 + 飞书告警，缺少指标（Metrics）和链路追踪（Tracing）
- 无法回答"过去一周盘中监控的平均延迟是多少"这类问题
- 告警只有飞书 Webhook，没有分级和收敛策略——可能被刷屏

**优化方案：**
- **日志**：当前 loguru 方案可行，但建议增加结构化日志字段（robot_id、trade_id、stock_code），便于检索
- **指标**：接入 Prometheus，上报关键业务指标（监控周期耗时、数据源成功率、交易执行延迟、每日盈亏）
- **告警分级与收敛**：分为 info/warn/critical 三级。info 走飞书群消息，warn 走飞书@指定人，critical 走电话或短信。同类告警5分钟内收敛合并，避免刷屏
- **链路追踪**：关键交易链路（选股→评分→下单→监控→卖出）串联一个 trace_id，出问题时可以完整回溯一笔交易的全生命周期
- **仪表盘**：建议用 Grafana 搭建运维看板，包含数据源可用性、调度任务执行状态、监控周期耗时分布、API 响应时间等

### 7.2 业务指标缺乏定义

**问题：**
- 文档中列出了 API 响应时间、数据源可用性等技术指标，但缺少业务维度的关键指标
- 系统是否正常工作不能只看技术层面——选股为空、连续亏损、净值异常这些业务异常同样需要监控

**优化方案：**
- **增加业务监控指标**：每日选股数量（为0则告警）、持仓数量变化、单日最大亏损、净值回撤超阈值、AHS 评分趋势
- **增加数据完整性监控**：当日龙虎榜数据是否到齐、K线数据是否有缺失、情绪数据是否更新
- **定义业务 SLA**：如"盘中监控延迟 P99 < 5秒"、"Phase B 执行成功率 > 99.9%"

## 八、前端架构

### 8.1 实时数据展示的性能风险

**问题：**
- AG-Grid + ECharts + LightweightCharts 三个重型组件同时使用，如果 Dashboard 页面同时渲染这三个组件，内存和 CPU 占用可能很高
- 实时行情通过 WebSocket 推送，如果推送频率高且股票数量多，频繁更新 DOM 会导致页面卡顿

**优化方案：**
- **实时数据推送到前端后做节流**（throttle），图表更新频率控制在每秒1-2次，不要每条消息都重绘
- AG-Grid 使用虚拟滚动，只渲染可视区域行
- **非当前可视页面的 WebSocket 订阅暂停**，切换到对应 Tab 时再恢复
- **重型图表组件做懒加载**，不在首屏全部初始化

### 8.2 前端状态管理边界不清

**问题：**
- Pinia 管理哪些状态、WebSocket 推送的数据如何与 Pinia 状态同步、缓存策略是什么都未定义
- 前端离线或 WebSocket 断开时如何保证数据展示的正确性

**优化方案：**
- **明确 Pinia 中的状态分类**：持久化状态（用户配置）、会话状态（当前选中的机器人）、实时状态（行情数据）
- **实时状态不要放入 Pinia**，直接用 reactive 对象管理，避免不必要的响应式追踪开销
- WebSocket 断开时前端展示最后一次数据并标记为"延迟"状态，而非显示空白

## 九、安全层

### 9.1 "初期单用户无需认证"的风险

**问题：**
- 即使单用户，如果部署在有公网 IP 的服务器上，任何人都可以访问 API 操控机器人（暂停、修改参数、触发交易）
- "后续加 JWT"意味着初期的 API 设计可能没有考虑认证中间件的接入点，后续改造成本高

**优化方案：**
- **最低限度**：Nginx 层加 IP 白名单或 Basic Auth
- 即使不实现完整认证，**API 框架中预留认证中间件的位置**（FastAPI 的 Depends），后续只需填充逻辑
- **关键操作接口（创建/删除机器人、修改策略参数、手动触发交易）必须从第一天就有鉴权保护**

### 9.2 数据源 API Key 管理

**问题：**
- TuShare 等数据源需要 API Key，文档中只提到 .env 不提交，但没有说明 Key 轮转、泄露后的处理方案
- 多个数据源的 Key 如果都放在同一个 .env 中，一旦泄露全部暴露

**优化方案：**
- **敏感配置建议使用密钥管理服务**或至少加密存储，不要明文放在 .env
- 定义 Key 泄露后的应急流程：轮转 Key → 检查历史调用 → 更新部署
- 不同数据源的 Key 分开管理，泄露一个不影响其他

## 十一、优先级排序

| 优先级 | 问题 | 影响 | 建议 |
|--------|------|------|------|
| **P0** | APScheduler 嵌入 FastAPI | 进程崩溃丢失所有调度，盘中监控中断 | 调度器独立部署，统一走 Celery |
| **P0** | 盘中监控无容错 | 数据源超时时错过止损窗口 | 加超时、降级、连续失败告警 |
| **P0** | Phase A/B 跨夜状态不一致 | 残留状态导致重复买入或漏买 | 状态持久化 + Phase B 前置检查 |
| **P1** | 数据源降级链粗粒度 | 不同数据类型降级路径不同 | 按数据类型分别配置降级链 |
| **P1** | 分档卖出并发安全 | 快速涨跌时重复卖出 | 交易执行加锁 |
| **P2** | WebSocket 设计粗糙 | 连接泄漏、推送风暴、断线无恢复 | 完善协议设计 + 心跳 + 背压 |
| **P2** | 监控体系不足 | 出问题后无法定位根因 | 补充指标上报 + 业务监控 + 链路追踪 |
| **P2** | API 缺少幂等和错误规范 | 重试导致重复操作、前端错误处理混乱 | 统一响应格式 + 幂等键 |
| **P3** | 前端实时渲染性能 | 多图表+高频推送导致卡顿 | 节流 + 懒加载 + 虚拟滚动 |
| **P3** | 发布策略缺失 | 交易时段更新导致状态混乱 | 定义发布窗口 + 向后兼容迁移 |
| **P3** | 回测任务管理不完整 | 无法取消、无进度反馈 | 补充任务生命周期管理 |

## 十二、已采纳的优化建议

| 评审项 | 采纳情况 |
