# 龙虎榜量化交易系统 v2 - 业务逻辑评审报告

> 评审日期: 2026-04-16
> 评审范围: 交易一致性、LLM风险、淘汰机制、合规风控、非功能性需求

---

## 一、交易一致性

### 1.1 资金流水的双重记账一致性

**问题：**
- `cash_ledger` 记录资金流水，`robot_trades` 记录交易，但两者之间没有数据库级别的约束保证一致
- 如果代码逻辑有 bug 或并发执行时序问题，可能出现"买入了但没扣钱"或"卖出了但没入账"的情况
- 审计时需要人工对比两张表才能发现不一致

**优化方案：**
- 交易执行时在同一事务内完成资金流水写入和交易记录写入
- 定期运行一致性校验任务：`SELECT robot_id FROM robot_trades WHERE status='open' GROUP BY robot_id` 的总市值应等于 `cash_ledger` 的资金余额
- 审计日志记录每次资金变动的前后余额，便于事后对账

### 1.2 并发卖出时的双重卖出保护

**问题：**
- 盘中监控和手动卖出可能同时触发，导致同一持仓被卖出两次
- 卖出执行后 `status` 更新和实际成交之间有时间窗口，多次监控轮询可能重复触发

**优化方案：**
- 在 `trade_executions` 表增加 `execution_id`（唯一约束）和 `idempotency_key`（robot_id + trade_id + sell_type + n）
- 同一 idempotency_key 的重复请求直接返回已有结果，不重复执行
- 卖出操作使用 `SELECT ... FOR UPDATE` 悲观锁

## 二、运行可靠性

### 2.1 定时任务失败补偿机制

**问题：**
- 如果 Phase A（18:50）因网络问题执行失败，当日选股结果缺失，无法补救
- 盘中监控如果某次执行失败，下一次执行时不知道上次的状态（是否触发了止损但没执行成功）
- Celery 任务失败后没有自动重试机制（需确认配置）

**优化方案：**
- 定时任务增加重试配置（最多3次，指数退避）
- 关键任务执行前检查是否已有成功执行的记录，防止重复执行
- 任务失败时发送告警并记录失败原因
- Phase A 失败后允许在 19:30 前手动补执行

### 2.2 集合竞价阶段的特殊处理

**问题：**
- 09:15-09:25 是集合竞价时段，此时没有实时成交价
- 如果 Phase B 在 09:35 执行，需要判断是否要等到实际开盘价
- 集合竞价期间的价格波动可能很大（涨跌停边缘），需要特殊风控

**优化方案：**
- Phase B 实际开盘后，用开盘价执行买入
- 增加"开盘价偏离度"检查：|开盘价 - 昨日收盘价| / 昨日收盘价 > 5% 则放弃买入
- 集合竞价阶段（09:15-09:25）暂不执行监控任务

## 三、时序正确性

### 3.1 时区统一

**问题：**
- Python 默认时区、数据库时区、前端展示时区必须统一
- 如果某处用 UTC 某处用 Asia/Shanghai，会导致日期错位（如凌晨 00:30 的数据被算成前一天）

**优化方案：**
- 数据库存储统一用 UTC，内部处理统一用 Asia/Shanghai
- 输出给前端时带上时区信息（ISO 8601 格式带 +08:00）
- 日志中记录时间戳，便于排查时区问题

### 3.2 停牌与除权处理

**问题：**
- 持仓股票如果中途停牌，监控任务应该如何处理？
- 除权除息日的价格跳空如何处理（止损线是跟着跳空还是维持原价格）

**优化方案：**
- 停牌股票跳过当日监控，不触发止损/止盈
- 除权除息日标记为特殊日期，暂停新开仓买入
- 止损线跟随除权调整（绝对价格止损），避免因除权导致止损无效

## 四、数据质量

### 4.1 龙虎榜数据完整性检查

**问题：**
- 龙虎榜数据是每日 16:00 左右才更新，如果当天数据采集失败就会缺失
- 数据缺失时选股服务应该能检测到并告警，而不是静默跳过

**优化方案：**
- 每日 18:30 检查当日龙虎榜数据条数，如果 < 50 条则告警（正常情况应该有 50-100 条）
- 缺失数据后尝试重新采集（数据源恢复后自动补采）
- 选股时如果某日数据缺失，该日不参与选股

### 4.2 数据源 API 频率限制处理

**问题：**
- AKShare 等免费数据源有 API 频率限制，超过限制会返回 429 错误
- 如果正在回填历史数据时触发限流，会导致部分日期数据缺失

**优化方案：**
- 回填任务增加请求间隔（如每分钟 30 次请求）
- 检测到限流后自动退避等待，然后继续
- 记录每个数据源的限制策略，便于调整

## 五、LLM 选股的特殊风险

### 5.1 LLM 调用不确定性

**问题：**
- LLM 响应时间不可控（几百毫秒到几十秒）
- 输出格式可能不稳定（JSON 解析失败）
- 相同输入多次调用可能得到不同结果

**优化方案：**
- LLM 调用设置严格超时（10 秒），超时直接走规则降级
- 返回结果做严格 schema 校验，失败走降级
- 记录每次 LLM 完整输入输出，用于审计和分析
- 相同输入在同一交易日缓存结果

### 5.2 LLM 降级策略验证

**问题：**
- 规则降级与 LLM 选股结果差异可能很大
- LLM 长期不可用时，系统可能一直在降级模式运行但无人知晓

**优化方案：**
- 统计 LLM 可用率和降级频率，降级率 > 30%/周 触发告警
- 规则降级结果同样经过评分和风控流程
- 定期对比 LLM 与规则的历史表现差异

## 六、机器人淘汰与进化

### 6.1 淘汰标准公平性

**问题：**
- 不同机器人创建时间不同，运行周期不同
- 新机器人样本量小，与老机器人用同一标准比较不公平

**优化方案：**
- 最低观察期：新机器人运行不满 20 个交易日不参与淘汰
- 淘汰评分考虑样本量置信度，交易次数少的惩罚更大
- 淘汰标准和评分公式可配置

### 6.2 淘汰后资源处理

**问题：**
- 被淘汰后如果还有未平仓持仓怎么处理？
- 淘汰机器人的历史数据是否保留？
- 被淘汰的机器人能否恢复？

**优化方案：**
- 淘汰前必须先平掉所有持仓
- 淘汰机器人历史数据永久保留，但不参与活跃统计
- 支持手动恢复被淘汰的机器人，恢复后重置观察期

### 6.3 模拟盘阶段

**问题：**
- 从开发直接到实盘，缺少观察期验证
- 没有定义"什么条件下可以从模拟盘切换到实盘"的准入标准

**优化方案：**
- robot status 增加 `paper_trading`（模拟盘）状态
- 模拟盘最短运行 20 个交易日
- 切换实盘准入标准：胜率 > 50%、最大回撤 < 10%、Sharpe > 1.0
- 模拟盘与实盘数据完全隔离

## 七、合规与风控边界

### 7.1 系统级硬性限制

**问题：**
- 所有风控都在策略层面，如果策略代码有 bug 则无最后防线
- 缺少系统级硬性约束

**优化方案：**
- 交易执行层（最底层）增加硬性限制：
  - 单笔买入不超过总资金的 20%
  - 单日交易总额不超过总资金的 50%
  - 单机器人累计亏损达到 20% 自动停机
- 这些硬性限制独立于策略参数，写在 app_config 中，不可被策略覆盖

### 7.2 交易频率监控

**问题：**
- 策略可能频繁交易（日内多次买卖同一股票）
- 多机器人同时买卖小市值股票可能影响市场价格

**优化方案：**
- 增加交易频率监控：单只股票日内交易次数、单日总交易次数
- 增加持仓集中度检查：单只股票占总资金比例上限
- 记录每笔交易的决策依据，便于审计

## 八、非功能性需求

### 8.1 系统启动顺序

**问题：**
- depends_on 只保证启动顺序，不保证服务就绪
- PostgreSQL 未初始化完成时 FastAPI 启动会报错

**优化方案：**
- 每个服务启动时做依赖就绪检查（health check loop）
- Docker Compose 的 healthcheck 配置真正检查服务可用性
- 启动顺序：数据库 → 执行迁移 → Redis → Celery Beat/Worker → FastAPI

### 8.2 优雅停机

**问题：**
- 盘中重启时，正在执行的监控任务、未完成的卖出操作如何处理
- Celery Worker 被 kill 时正在执行的任务会丢失

**优化方案：**
- FastAPI 和 Celery Worker 实现优雅停机
- 关键任务设置超时上限，防止无限等待
- 停机前自动检查未完成的交易操作并告警

### 8.3 配置分层

**问题：**
- 配置分散在 .env、app_config、strategy_params、robots 多处
- 同一概念（如止损率）可能在多处出现
- 配置优先级和覆盖关系不明确

**优化方案：**
- 配置层级：.env → app_config → strategy_params → robots
- 覆盖规则：实例级 > 策略级 > 全局级
- 配置变更全部记录审计日志

## 九、完整优先级汇总

| 优先级 | 类别 | 关注点 |
|--------|------|--------|
| **P0** | 交易一致性 | 资金流双重记账一致性、并发卖出的锁机制 |
| **P0** | 运行可靠性 | 定时任务失败补偿、优雅停机、启动依赖检查 |
| **P0** | 风控兜底 | 系统级硬性限制（独立于策略）、集合竞价异常保护 |
| **P1** | 时序正确性 | 时区统一、交易时段边界处理、停牌/除权处理 |
| **P1** | 数据质量 | 数据源频率限制、入库前校验、龙虎榜数据完整性检查 |
| **P1** | LLM 风险 | 超时降级、输出校验、可复现性记录、降级率监控 |
| **P1** | 淘汰机制 | 公平性、淘汰前平仓、模拟盘准入标准 |
| **P2** | 策略管理 | 参数热更新对已有持仓的影响 |
| **P2** | 运维 | 连接池管理、日志磁盘空间、audit_log 归档 |
| **P3** | 合规 | 交易频率监控、持仓集中度、决策链可追溯 |
| **P3** | 配置管理 | 配置分层、优先级覆盖、变更审计 |
| **P3** | 状态机 | 交易状态严格定义、非法转换拒绝 |
