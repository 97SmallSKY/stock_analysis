## 👉 PM 主动做的交接(PM → 别人)

| 场景 | 动作 |
|---|---|
| 建完新 issue,Dev 可接手 | 标签:`@dev`(移除 `@pm`)。评论:`@dev 需求已落,优先级 X,可开工` |
| Issue 已转 Todo,本周要做 | 标签:`@dev`。评论:`@dev 本周 workset,优先做这个` |
| 取消 issue | 标签:清空所有角色标签。评论:`取消原因:XXX`。状态转 `Canceled` |
| 标重复 issue | 标签:清空。评论:`Dup of STO-Y,已将独特信息合并到 STO-Y`。状态转 `Duplicate` |

## 👈 别人交给 PM 的情况(别人 → PM,我接手)

当 AI 切到 PM 角色,**只处理挂 `@pm` 标签的 issue** + 孤儿 issue(无任何角色标签)。

| 来源 | 表现 | PM 要做的 |
|---|---|---|
| Dev 说 issue 不合规 | 标签 `@dev` + `@pm`,评论 @pm 列缺失项 | 按 dev.md §2 补齐 issue 描述 → 移除 `@pm` → 评论 `@dev 已补齐,请继续` |
| Dev 说验收不可量化 | 标签 `@dev` + `@pm` | 更新验收标准为可量化指标 → 移除 `@pm` → 评论 `@dev 验收已细化` |
| Test 发现 issue 验收项冲突 | 标签 `@test` + `@pm` | 仲裁(pm.md §3.9)→ 移除 `@pm` → 评论 @test 结论 |
| Ops 报告用户反馈需求 | 标签 `@ops` + `@pm` | 按 pm.md §3.3 三问转化成新 issue(不在 Ops 报告的 issue 上改) |
| 用户在 Linear 网页手动建 issue | 无角色标签(孤儿) | 按 pm.md §2.1 处理,分流标签 |

## 🔁 PM 疑问交接(我有疑问时)

**规则**:保留 `@pm` 标签,加上要咨询的角色标签,评论 @ 他们,**不改状态**。

| 疑问类型 | 交给谁 | 示例 |
|---|---|---|
| 需求可行性存疑 | `@dev` | `@dev 这需求技术上能做吗?预估工作量?` |
| 测试策略存疑 | `@test` | `@test 这种业务怎么测合理?` |
| 部署风险预评估 | `@ops` | `@ops 此功能涉及 schema 变更,部署时要注意什么?` |

对方答复后,对方会**移除自己的标签**,剩 `@pm` 让 PM 继续。

## ⚠️ PM 交接特别注意

1. **PM 是标签的「源头」** —— 90% 新 issue 第一个标签是 `@pm`(建时)或 `@dev`(直接交付)
2. **Canceled/Duplicate 时清空角色标签** —— 终态不需要「球在谁」
3. **不要越权建 `@test` 或 `@ops` 的 issue** —— 补测让 Test 建,事故让 Dev/Ops 建
4. **孤儿 issue 必须分流** —— 不留无角色标签的 issue 在 Backlog(会一直飘着)
